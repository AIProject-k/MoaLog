# 사진 자동분류 (에이닷 로그류)

사진 폴더를 스캔해 **자동 분류 · 정리 · 타임라인 · 자연어 검색**을 하는 로컬 앱.
Windows 데스크톱이 1차 대상이지만, 목적은 데스크톱 제품이 아니라
**안드로이드로 옮기기 전 분류 품질을 빠르게 재고 튜닝하는 테스트베드**다.

## 설계의 중심

임베딩 모델 **하나**가 기능 4개 중 3개를 덮는다.

| 기능 | 구현 | 추가 모델 |
|---|---|---|
| 자동 분류 | 카테고리 문장 임베딩과 코사인 유사도 (zero-shot) | 0 |
| 자연어 검색 | 검색어 임베딩과 코사인 유사도 — **분류와 같은 연산** | 0 |
| 유사/중복 | 이미지 임베딩끼리 코사인 유사도 | 0 |
| 타임라인 | EXIF 촬영시각만 사용 | 0 (AI 불필요) |

학습 0회, 카테고리별 분류기 0개, 벡터DB 0개.
카테고리 추가 = `config.json`에 문장 한 줄.

## 설치 · 실행

```bash
pip install pillow numpy onnxruntime tokenizers fastapi uvicorn python-multipart send2trash
```

```bash
python setup_model.py       # 영어 모델 (비교 기준용)
python export_ko_model.py   # 한국어 모델 (기본) — torch 필요, 1회만
```

기본은 **한국어 CLIP** (Bingsu/clip-vit-base-patch32-ko, MIT, 164MB).
검색어를 한국어 그대로 받으므로 번역 사전이 필요 없다.
`export_ko_model.py`는 torch/transformers를 쓰지만 **앱 실행에는 필요 없다** —
결과물인 `.onnx` + `tokenizer_ko.json`만 있으면 onnxruntime으로 돌아가고,
그 파일이 그대로 안드로이드로 간다.

`config.json`의 `model_variant`를 `"en"`으로 바꾸면 영어 모델 + 사전 번역 방식으로
되돌아간다 (비교용). **모델을 바꾸면 기존 임베딩이 자동으로 무효화되고 다시 계산된다** —
서로 다른 공간의 벡터를 비교하면 검색 결과가 엉키기 때문이다.
**이 파일 없이도 앱은 돈다** — 규칙 태그·타임라인·완전중복은 그대로 동작하고
CLIP 분류와 자연어 검색만 빠진다.

```bash
python app.py
```

`localhost:8000`이 열린다. 폴더 경로를 붙여넣거나 사진을 끌어다 놓으면 된다.

## 분류 정확도 재기

```bash
python eval/fetch_dataset.py 50
```

Wikimedia Commons에서 자유 라이선스 사진을 8분류 × 50장 받는다
(CC0/퍼블릭도메인 우선, 출처는 `eval/ATTRIBUTION.csv`에 전량 기록).
**검색어 자체가 정답 라벨**이라 별도 어노테이션이 필요 없다.

```bash
python eval/score.py [en|ko]          # 분류 정확도
python eval/score_search.py [en|ko]   # 한국어 검색 P@10
```

카테고리별 precision/recall/F1과 혼동행렬. 앱과 **똑같은 코드 경로**로 분류하므로
여기 숫자가 곧 앱의 성능이다. 분류는 내가 써 둔 고정 프롬프트를 쓰지만 검색은
사용자가 아무 말이나 치므로 `score_search.py`로 따로 잰다.

> Commons는 미술관·도서관 아카이브라 스캔한 판화·스케치가 섞여 들어온다.
> MET이 "Mountain Landscape"라 이름 붙인 연필 스케치북 페이지를 '풍경' 정답으로
> 쓰면, 그걸 '문서'라 답한 분류기가 오답 처리된다. `fetch_dataset.py`가
> 사진 카테고리에서 스캔본을 검색·제목 두 단계로 걸러내는 이유다.

```bash
python test_pipeline.py
```

자체 점검. 프레임워크 없이 `assert`만 쓴다.

```bash
python eval/make_fixtures.py            # 안드로이드 패리티 계약 생성
python eval/make_fixtures.py --verify   # 지금 코드가 그 계약을 지키는지 대조
```

`eval/fixtures/`에 **폰이 맞는지 아닌지를 가르는 기준선**을 만든다 — 한국어 305문장의
토큰 id, 그 문장들의 임베딩, 사진 64장의 임베딩과 1순위 라벨. 폰에서 같은 값이 나오면
여기서 잰 정확도가 폰의 정확도다.

`--verify`는 데스크톱 자신을 대조한다. 전처리를 건드렸을 때 조용히 어긋나는 것을 잡는다
(보간을 BICUBIC으로 되돌리면 이미지 코사인이 0.972로 떨어지며 위반이 뜬다).

## 측정 결과 (2026-09-01, 400장)

### 한국어 검색 정확도 P@10 — 한국어 모델을 쓰는 이유

`python eval/score_search.py [en|ko]`

| | 영어 CLIP + 사전 번역 | **한국어 CLIP** |
|---|---|---|
| 사전에 **있는** 말 (고양이, 영수증…) | 0.83 | **0.89** |
| 사전에 **없는** 말 (접시에 담긴 요리…) | **0.40** | **0.78** |
| 전체 | 0.69 | **0.87** |

영어 모델은 `ko_dict`에 없는 말이 나오면 한글이 그대로 CLIP에 들어가 결과가
'그럴듯하지만 무의미'해진다. "접시에 담긴 요리"·"종이에 적힌 글씨"가 0.1 → 1.0으로
바뀐 것이 그 차이다. 한국어 모델은 사전 자체가 필요 없다.

### 분류 정확도 — 두 모델이 동등

| | 영어 CLIP | 한국어 CLIP |
|---|---|---|
| 전체 정확도 | 0.86 | **0.86** |
| 평균 F1 | 0.87 | 0.86 |
| 미분류 | 5장 | 1장 |

즉 **한국어를 얻으면서 분류 품질은 잃지 않았다.** 크기도 156MB → 164MB로 거의 같다.

아래 표는 영어 모델 기준 (분류별 경향은 두 모델이 비슷하다).

CLIP ViT-B/32 int8 · CPU 13~16ms/장 · **전체 정확도 0.86 · 평균 F1 0.87**

| 분류 | precision | recall | F1 |
|---|---|---|---|
| 화면캡처내용 | 1.00 | 0.96 | **0.98** |
| 실내일상 | 0.96 | 0.96 | **0.96** |
| 반려동물 | 0.96 | 0.92 | **0.94** |
| 음식 | 0.92 | 0.94 | **0.93** |
| 풍경/여행 | 0.86 | 1.00 | **0.93** |
| 상품/쇼핑 | 0.95 | 0.70 | 0.80 |
| 문서/영수증 | 0.70 | 0.92 | 0.79 |
| 인물 | 0.70 | 0.52 | **0.60** ← 약점 |

400장 스캔(썸네일·EXIF·SHA-256·CLIP 전부 포함) **9초**.

**인물 F1 0.60은 실제보다 비관적인 값이다.** 오분류 25장을 눈으로 확인한 결과
(a) 일몰 실루엣 풍경 사진이 'people' 검색에 딸려 와 인물 정답으로 잘못 붙었고
(b) Fortepan 등 아카이브의 스캔된 옛 인화물이 섞여 있었다.
실제 휴대폰 갤러리에는 없는 종류다. 필터를 두 번 걸어도 Commons에서는 완전히 못 걷어낸다.

### 되돌린 시도 (반복하지 말 것)

문서 프롬프트를 "화면을 채운 평면 문서"로 좁혀 행사 사진 오분류를 줄이려 했으나,
**스크린샷이 대신 들어와** 화면캡처 recall이 0.96 → 0.76으로 무너졌다 (전체 0.86 → 0.83).
스크린샷도 글자로 꽉 찬 평면이라 같은 문장에 걸린다.
문서와 화면캡처는 문장만으로는 못 가른다 — 규칙 태그(EXIF 카메라 유무)를 써야 한다.

### 성능

400장 전체 처리 **8.9초 = 장당 22.3ms** (1만 장 3.7분).

배치 추론을 껐기 때문에 5.8초(14.4ms)보다 느리다 — 이유는 바로 아래. 그 전의
이미지 처리 최적화(24.3 → 14.4ms)는 그대로 유효하다.

프로파일링 결과 **병목은 CLIP이 아니었다.** 장당 24.3ms 중:

| 단계 | 최적화 전 | 비중 |
|---|---|---|
| 썸네일 생성·저장 | 5.5ms | 27% |
| JPEG 디코드 | 3.9ms | 19% |
| 선명도·밝기 | 3.5ms | 17% |
| CLIP 추론 (배치 32) | 7.2ms | 35% |
| EXIF + SHA-256 | 0.6ms | 3% |

고친 것 세 가지 — 전부 **이미지 처리** 쪽이다:

1. **필요 이상으로 디코드하지 않는다.** `decode_px`를 512→320으로. CLIP은 224면 되고
   썸네일은 320이면 된다. draft 384/320/256으로 실측했을 때 정확도는 0.853~0.863 사이
   무작위 변동뿐이었다 — **디코드를 키워도 정확도는 안 오른다.**
2. **흐림 점수는 L로 먼저 바꾸고 줄인다.** 1채널 리사이즈가 RGB보다 3배 싸다.
3. **불필요한 `im.copy()` 제거.** `base`가 별도 객체면 `im`을 그대로 썸네일로 줄여도 안전하다.
   썸네일 보간도 LANCZOS→BILINEAR+`reducing_gap`.

정확도 영향: 0.865 → 0.860 (400장 중 2장, 노이즈 범위).

### 추론은 1장씩 넣는다 — 배치가 임베딩을 바꾼다

속도만 보면 배치 32가 최적이다 (1장 15.2ms / 16장 8.0ms / 32장 7.2ms / 64장 9.4ms).
**그런데 배치로 넣으면 같은 사진이 매번 다른 벡터를 받는다.**

int8 동적 양자화는 활성값 스케일을 추론 시점에 잡는데, 그 스케일이 **배치 텐서 전체**에서
나온다. 그래서 한 사진의 임베딩이 같은 배치에 우연히 들어간 다른 사진에 좌우된다. 400장 실측:

| 비교 | 같은 사진의 코사인 (중앙 / 최소) | 1순위 라벨이 뒤집힌 장수 |
|---|---|---|
| 배치 1 vs 배치 32 | 0.9871 / 0.9522 | 5 / 400 |
| **스캔 순서만 섞음** (둘 다 배치 32) | 0.9857 / **0.9435** | **11 / 400** |

전체 정확도는 0.863 ↔ 0.865로 멀쩡하다 — **집계로는 안 보이고 사진 단위로만 보인다.**

그냥 둘 수 없는 이유는 잡음의 크기다. 최소 0.9435는 `dupe_similarity`(0.95)와 같은 값이다.
*같은 사진끼리도* 중복 판정을 통과하지 못할 수 있고, 폴더를 다시 스캔하면 파일 순서가 바뀌어
중복 그룹과 검색 결과가 달라진다. 재현되지 않는 인덱스는 인덱스가 아니다.

`config.json`의 **`infer_batch: 1`**이 이걸 막는다. 배치가 1이면 스케일이 그 사진에서만
나오므로 임베딩이 사진만의 함수가 된다. 대가는 장당 14.4 → 22.3ms.
`batch_size`(32)는 DB 커밋 단위라 별개이고 그대로 둔다.

속도가 정말 문제가 되면 **정적 양자화**(교정된 고정 스케일)로 올린다 — 그러면 배치를
되살릴 수 있다. 그 전엔 1을 유지할 것.

### 분류 체계 (2026-09-02 확장)

**카테고리 14 · 세부 종류 59 · 속성 14.** 정확도 0.86, 태그 포함율 0.90. 늘리면서 배운 것:

- **카테고리는 제로섬이다.** 8→14개로 평면 확장하니 0.86 → 0.82. 인물 7장이 '행사/축제'로 갔다.
- **하위 종류는 계층으로.** `subcategories_ko`는 부모가 정해진 뒤 형제끼리만 softmax를 돈다 —
  다른 부모의 표를 안 빼앗아 부모 정확도가 그대로다.
- **`classify_min_score`는 개수에 딸린 값.** 8개 0.25 → 14개 0.16 (미분류 7 → 1장).
- **속성은 속성별 임계값**(`attr_thresholds_ko`). 전역값 하나면 '지도화면'이 풍경에, '눈비'가
  반려동물에 붙는다. 신호 없는 속성(눈비·역광·꽃)은 버렸다.
- **프롬프트 템플릿**(`prompt_templates_ko`) 3개 앙상블로 +2점 (0.838 → 0.858).

카테고리를 또 늘리면 `python eval/score.py ko`로 기존 것이 얼마나 나빠졌는지 **반드시** 다시 잴 것.

## 튜닝

**모든 임계값과 프롬프트는 `config.json`에만 있다.** 코드에 상수를 박지 않는다.
사진 해상도·기기·촬영 습관마다 최적값이 다르고, 안드로이드로 넘어갈 때
이 파일이 그대로 가기 때문이다.

두 임계값은 **척도가 다르다**:
- `classify_min_score` — softmax 확률 (0~1)
- `attr_tag_threshold` — CLIP 원 코사인. 속성 태그는 서로 배타적이지 않아 softmax를 못 쓴다.

원 코사인은 **모델마다 분포가 다르므로 variant별로 둔다** (`attr_tag_threshold_ko`, 없으면 공용값).
en 기준값 0.24를 ko에 그대로 쓰면 사실상 꺼진다 — ko는 400장에서 어느 속성도 0.271을 넘지
않아 0.24가 p99 위였고, '셀카'가 400장 중 2장에만 붙었다. ko 기본값은 0.225다:

| 임계 | 텍스트많음 (기대 100장) | 실외 (풍경 50장) |
|---|---|---|
| 0.220 | 77장 적중 / 110장 부착 | 44 / 91 |
| **0.225** | **61 / 77** | **38 / 81** |
| 0.240 | 28 / 29 | 13 / 27 |

`blur_threshold` 기본값은 **0**(아무것도 제안 안 함)이다. 흐림 기준은 카메라마다
달라서 기본값을 정할 수 없다 — 정리 탭이 실제 선명도 분포를 보여주니
그걸 보고 슬라이더로 정하면 된다.

## 안전장치

정리 기능은 **파일을 삭제하지 않는다.** 확인 후 휴지통으로만 보낸다.
놓친 중복은 다음에 잡으면 되지만 잘못 지운 사진은 돌아오지 않는다.

- 한 중복 그룹의 사본을 전부 선택해도 **1장은 남긴다** (서버가 강제)
- 중복 중 '남길 것'은 스캔 순서가 아니라 **파일명으로 원본을 판별**한다
  (`- 복사본`, `(1)`, `Copy` 접미사가 붙은 쪽이 사본)
- 흐림·저품질 제안은 기본이 **체크 해제**

## 안드로이드 포팅

전체 설계는 [ANDROID.md](ANDROID.md). 아래는 요약.

| 그대로 감 | 다시 짬 |
|---|---|
| `models/*.onnx` (ONNX Runtime Mobile) | Python → Kotlin |
| `config.json` (프롬프트·임계값·한글사전) | FastAPI → 없음 |
| SQLite 스키마 → Room | HTML → Compose |
| 판정 로직과 단계 순서 | 폴더 스캔 → MediaStore |

데스크톱에서 돌린 바로 그 `.onnx`가 안드로이드에서도 돌기 때문에,
여기서 튜닝한 임계값과 프롬프트가 그대로 유효하다.
`READ_MEDIA_IMAGES` 권한과 Play Store 심사는 포팅 단계에서 미리 확인할 것.
